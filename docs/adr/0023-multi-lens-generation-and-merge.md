# ADR 0023: Multi-lens generation and merge

Date: 2026-07-03
Status: Accepted

## Context

ADR 0022 decoupled recall from precision within a single generator: enumerate candidates wide, verify each, score confidence, gate deterministically. It deferred the stronger recall lever, independent parallel generators, reasoning that the gate and the generate-verify-score method needed to be proven single-agent first.

`review-agent-default`'s prompt, per ADR 0022, already enumerates cross-component state divergence, caller-contract mismatch, and co-varying-state assumptions, the class a prior single-pass review missed on a confirmed cross-component divergence bug. A focused lens does not need to teach the pipeline a new candidate *class* for that gap; the win is a second independent read that is not competing for attention with the rest of the taxonomy (polish, refactor, style triage) the default agent also carries.

Anthropic's own code-review skill was the reference point for going wider than one focused lens: its documented architecture runs four fixed domain lenses (security, performance, correctness, style) and always includes correctness alongside security and performance, never treating it as optional in favor of the other domains (Anthropic, "Code Review" agent skill documentation, verified 2026-07-03).

## Considered options

- **Only a focused correctness/data-flow lens (rejected as final scope, shipped as an intermediate step).** `review-agent-correctness` alone targets the motivating gap at 2x cost. Cheapest option and the one the ship-the-core-then-expand precedent ADR 0022 set favors starting from, but it leaves the security/performance/test-quality classes those dormant agents were written for entirely uncovered.
- **Activate `perf`/`security`/`tests` without a correctness lens (rejected).** This was this project's original placeholder framing for "the Anthropic-style option," but the actual Anthropic skill's four-lens reference includes correctness as a first-class member. Skipping it to add perf/security/tests instead would cover different bug classes while leaving the class that motivated this ADR no better off than the single-generator design alone.
- **All four domain lenses alongside default (chosen): correctness, perf, security, tests.** Matches the Anthropic skill reference more faithfully (security, performance, correctness, and a style-adjacent quality lens, test-quality standing in for this codebase's dormant `tests` agent rather than prose style, which `review-agent-default` already owns) and activates every dormant lens `docs/persona-design.md` had scoped since V1 instead of leaving three idle indefinitely. 5x per-tick cost.
- **Dispatch the 5 lenses serially, reusing ADR 0013's `MAX_PARALLEL` as the only concurrency bound (superseded, see Decision 2).** The initial cut ran lenses one after another specifically to avoid multiplying `MAX_PARALLEL` by the lens count. This turned out to conflate two independent concerns: `MAX_PARALLEL` bounds concurrent review-pr.sh *processes*, but nothing in that design bounds concurrent `claude -p` *calls* directly, so the real safety property (bounded concurrent API load) had no dedicated mechanism, only an emergent one. It also meant the outer per-PR watchdog (`PER_PR_TIMEOUT`) had to be sized to the full sequential sum of all 6 agent calls, ballooning to 2100s. Superseded by Decision 2's shared slot pool, which bounds `claude -p` concurrency directly and lets lenses run in parallel.

## Decision

1. **Four new lens agents**, each mirroring `review-agent-default`'s inputs, voice, prose style, and output contract exactly and differing only in scope:
   - **`review-agent-correctness`** (`.claude/agents/review-agent-correctness.md`): cross-component state divergence, caller-contract mismatch, co-varying-state assumption, async/ordering divergence.
   - **`review-agent-perf`** (existing placeholder, filled in): N+1 query/request patterns, hot-path asymptotic cost, unnecessary allocation/copy, blocking I/O on a path that shouldn't block.
   - **`review-agent-security`** (existing placeholder, filled in): auth/authorization gaps, injection, input validation gaps at a trust boundary, secrets in the wrong place, other OWASP top-10 classes with a concrete exploit path.
   - **`review-agent-tests`** (existing placeholder, filled in): missing coverage for a newly-exercised path, flaky patterns, over-mocking, weak assertions.

   Each ships with its own dispatch command (`/review-pr-correctness`, `/review-pr-perf`, `/review-pr-security`, `/review-pr-tests`), same `Finding`/`ReviewPayload` schema, same confidence rubric. Voice is intentionally shared rather than persona-per-domain (the earlier `docs/persona-design.md` guidance, written before this multi-lens merge design existed, suggested a bespoke voice per new agent): all five lenses' findings merge into one posted review, so a fragmented per-lens voice would read as inconsistent to the PR author. The domain-specific prompt content is the differentiator, not tone.

2. **`daemon/review-pr.sh` dispatches all five lenses in parallel**, each bounded by a new global slot pool (`acquire_claude_slot`/`release_claude_slot`, `daemon/lib.sh`) instead of by `MAX_PARALLEL`. The pool is `CLAUDE_SLOT_POOL_SIZE` numbered lockfiles (code fallback 3 if truly unset anywhere; the shipped `templates/.env.example` recommends 10, enough for two PRs' lens phases to fully overlap, since a pool sized only for one PR's own 5 lenses gives zero headroom for any other concurrent PR to make progress even with `MAX_PARALLEL` raised), using the same noclobber-plus-stale-reclaim mechanism as the existing per-PR lock (macOS has no `flock`): a lens acquires a slot (blocking, unlike the per-PR lock's non-blocking contract, since a lens should wait for a slot rather than skip the PR on contention), runs its `claude -p` call, and releases the slot in the same subshell regardless of success, timeout, or failure. Because the slot files live on disk rather than in one process's memory, every concurrently-running `review-pr.sh` process shares the same pool automatically; `MAX_PARALLEL` (ADR 0013) and the slot pool now bound two genuinely different resources without either script needing to know about the other. `MAX_PARALLEL` bounds concurrent review-pr.sh *processes* (disk, scratch clones, non-`claude -p` overhead); the slot pool bounds concurrent `claude -p` *calls* directly, which is the resource that actually needs rate-limit protection, so `MAX_PARALLEL` can be raised freely for process-level throughput without reopening the concurrent-API-load risk ADR 0013 was written to contain. Dispatch itself is a background loop over `LENS_COMMANDS`/`LENS_LABELS`/`LENS_RAW_FILES` (plain indexed arrays, not associative, since ADR 0013 already established the runtime is stock macOS bash 3.2), followed by a `wait` loop that checks each backgrounded PID's own exit status in dispatch order, independent of which lens actually finishes first. The default lens keeps ADR 0005's original unprefixed failure categories (`review-timeout`, `empty-stdout`), pinned elsewhere (`test_log_styling.py`, `test_status_comment.py`); every other lens gets a `<label>-` prefix (`correctness-review-timeout`, `perf-empty-stdout`, etc.) so a stuck lens is diagnosable without ambiguity in `.daemon.log`. `status_failure_reason` (`daemon/lib.sh`) maps every lens's timeout category to the same author-facing "The review agent timed out." phrase via a `*-review-timeout` glob, not a literal enumeration, since which internal generator stalled is not something the author can act on and a future lens's category must not need a code change here to be recognized. `daemon/stream_format.py` gains an optional `--label` that tags each live progress line (e.g. `[correctness]`); concurrent lenses now share one terminal, so their previously-implicit ordering can no longer disambiguate which lens a line came from. The editor, which structurally cannot start until `merge_findings.py` has combined every lens's output, stays sequential after the lens phase but still acquires a slot around its own call, since other PRs' lenses or editors may be competing for the same pool concurrently.

3. **`daemon/merge_findings.py`** (new) unions all five lenses' payloads before the confidence gate runs, not after, and dedups within each `(path, line)` group by body-text similarity (`difflib.SequenceMatcher`, threshold 0.5), not by collapsing the whole group outright. Two lenses can flag genuinely different defects on the same line (one lens's null-deref, another's off-by-one); a bare `(path, line)` collapse would silently drop the distinct one, so `_combine` clusters same-location findings by how alike their bodies read and merges only within a cluster. Within a cluster, the finding with the higher scored confidence stands in (its body is presumed better-verified), and if nothing in the cluster is scored the first is kept (`None` means unscored, gate-exempt, not zero). `daemon/extract_json.py` is split: `parse_payload` (fence, JSON, schema, optional style) and `enforce_cap` are now standalone, and `extract()` composes them with the existing gate for the single-payload path unchanged (behavior-preserving; the existing extract_json test suite passes without modification). Gating post-merge is what lets same-defect overlap raise effective confidence: a location one lens scores 70 and another scores 88 clears an 80 threshold on the merged 88, where either lens alone would have been gated or kept unmerged. The merge is lens-count-agnostic: `merge()` takes a list of raw payloads of any length, so five lenses need no different code path than two. Past the gate, a merged set larger than `MAX_FINDINGS` (10, sized for one generator) is truncated to the top 10 by severity then confidence, not hard-failed the way `extract_json.enforce_cap` fails a single payload: every lens obeyed its own "at most 10" instruction, so a union exceeding 10 is an expected byproduct of merging well-behaved lenses, not evidence of a misbehaving one, and hard-failing would discard every already-completed lens's output over that byproduct.

4. **`daemon/review-pr.sh` calls `merge_findings.py` in place of the single-payload `extract_json.py --no-style` call**, feeding all five raw lens outputs (`"${LENS_RAW_FILES[@]}"`). Everything downstream (editor, `apply_edits.py`, anchoring, posting) is unchanged; `merge_findings.py`'s output is schema-identical to `extract_json.py`'s.

5. **`bundle_operator_agents` (`daemon/lib.sh`)** picks up all four new agent files via its existing `review-agent-*.md` glob, and all four new dispatch commands via a matching `review-pr-*.md` glob added alongside the explicit list for the non-lens commands (`review-pr.md`, `edit-review.md`, `reply-pr.md`, `judge-fix.md`, which aren't name-prefixed the same way). Without a bundling path for a new lens's slash command, it would never reach the scratch clone and every dispatch of it would fail in production despite passing locally, where the repo's own `.claude/commands/` is on disk; the glob means a future lens needs no update here.

6. **`PER_PR_TIMEOUT`'s default (`daemon/lib.sh`) rises from 600s to 1800s** (revised again in Decision 9). The outer per-PR watchdog (#121) was sized for one inner `claude -p` call. With the lens phase parallelized (Decision 2) and `CLAUDE_SLOT_POOL_SIZE` set to at least the lens count (5), a solo PR's own lenses need no internal wait, so the realistic sequential shape is two stages, the lens phase then the editor, plus clone/fetch/diff/anchor/post overhead, plus a margin for cross-PR contention when the shared slot pool is also serving other concurrently-running PRs (`MAX_PARALLEL` > 1). This is a realistic planning number, not a guarantee against the full pathological worst case (every concurrent PR maxing out the pool at once), which is unbounded for any shared resource pool by construction. A run that hits this bound under genuinely heavy contention fails and retries next cycle, poll.sh leaves state untouched on a failed dispatch, so this is a cheap, self-healing failure mode, not data loss, and the bound is chosen to trade some detection latency rather than chase an unbounded worst case. `PER_PR_TIMEOUT` is shared with `reply-pr.sh`'s single-agent-call path, whose own worst case is comfortably inside this bound.

7. **`gh pr diff` (`daemon/review-pr.sh`) gains its own `GH_API_CALL_TIMEOUT` (default 90s).** Raising `PER_PR_TIMEOUT`'s default widened the window before this specific unbounded `gh` call (not a git operation, so `arm_git_stall_timeout`'s low-speed thresholds do not cover it) would be caught if it hung, from 600s to whatever the new bound is. A dedicated, tight timeout restores fast detection for this one call independent of the outer bound's size, with its own `diff-fetch-timeout` failure category and `status_failure_reason` phrase ("Fetching the PR diff timed out."). The status-comment `gh api` calls (`find_status_comment`, `post_status_comment`, `edit_status_comment`) have the same gap and are not addressed here: each wraps a pipeline (not a single command), so adding a timeout safely needs more care than this single-command fix.

8. **A cap-truncation count reaches the posted summary, not just `.daemon.log`.** `merge_findings.py` emits a machine-parseable `truncated_count=<n>` stderr line alongside its existing human-readable one (mirroring `ExtractError`'s `category=` convention); `daemon/review-pr.sh` greps it out and passes `--truncated-count` to `daemon/apply_edits.py`, which appends a count sentence to the final summary *after* the Editor's voice gate has already run (fixed UI chrome, not agent prose, so it is authored 두괄식 and em-dash-free by hand rather than routed through `voice.py`). Mirrors Anthropic's own code-review plugin, which caps nit comments and mentions the rest as a count in the summary rather than dropping them with no visible trace.

The following three decisions came from dogfooding this design against a real multi-PR workload (`taewanu/sounds-abroad`, `MAX_PARALLEL=2`, `CLAUDE_SLOT_POOL_SIZE=10`), not from design review alone.

9. **`REVIEW_AGENT_TIMEOUT`/`EDITOR_AGENT_TIMEOUT` rise from 300s to 600s; `PER_PR_TIMEOUT` rises again to 1800s.** A real dogfood run showed successful lens completions of 178-262s even in the least-contended case (one completion cleared the 300s cap with only 38s to spare), and 3 of 4 reviews in the same cycle failed on exactly this timeout. Narrowing a lens's scope (Decision 1) does not proportionally shrink its cost: the generate-verify-score method (ADR 0022) spends its time verifying each candidate against the code regardless of how few candidate classes it's checking, and real contention on the shared slot pool (10 concurrent `claude -p` calls at once, from two PRs' lens phases overlapping) plausibly slows individual calls further. `PER_PR_TIMEOUT`'s realistic-planning-number reasoning (Decision 6) still holds, just recomputed against the new per-call caps.

10. **`merge_findings.merge()` no longer aborts the whole merge on one lens's parse failure.** The same dogfood run hit a concrete case: one lens emitted `severity: "minor"` (not a valid `Finding` enum value), and the resulting `schema-invalid` `ExtractError` crashed the merge before the other four lenses' already-completed, valid findings were ever unioned, discarding real work purely because one generator slipped on a prompt-adherence detail. `merge()` now parses each lens payload independently, catching `ExtractError` per lens, logging which lens failed and why (`merge-skip: <label> payload failed (<category>): <message>`) to stderr, and proceeding with whatever parsed. Only every lens failing is fatal (`all-lenses-failed`, a new category that falls into `status_failure_reason`'s existing silent default like other internal pipeline hiccups). This is the same "one bad component must not sink everyone" principle Decision 3's cap-truncation already applies, extended to parse failures. `main()` derives each lens's label from its raw-output filename (`_label_from_path`, e.g. `.pr-review-raw-correctness.txt` → `"correctness"`) purely for this diagnostic message; it has no bearing on merge semantics.

11. **`stream_format.py`'s `--label` now carries PR identity, not just lens identity** (`pr186:correctness`, not `correctness`). With lenses parallel within a PR (Decision 2) *and* multiple PRs running concurrently (`MAX_PARALLEL` > 1), a lens-only label is ambiguous: `[correctness]` could be PR 185's or PR 186's. `daemon/review-pr.sh` composes the label as `pr${PR_NUMBER}:${lens_label}` (and `pr${PR_NUMBER}:editor` for the editor call) before passing it through.

A second dogfood round (same workload, after Decisions 9-11 landed) surfaced three more operator-facing gaps, all fixed without a design change:

12. **`claude`'s own stderr goes to a per-call sidecar file, not the primary log.** Every `claude -p ... | stream_format.py` pipe only ever piped stdout; claude's stderr (chiefly its non-interactive workspace-trust notice, since a fresh scratch clone is never pre-trusted and non-interactive mode has no bypass for that) flowed straight through, unlabeled and outside stream_format.py's formatting, flooding the log once per lens per PR per tick. All four call sites (lenses, editor, judge-fix, reply agent) now redirect `2>"$raw_file.stderr"`: nothing is silently lost, but the primary log stays legible. The underlying permission-ignore gap this notice describes is unresolved (a real fix needs a fixed, reused pool of scratch dirs manually trusted once each); only the log noise is addressed here.

13. **`stream_format.py`'s labels are now coloured per-PR**, reusing `daemon/lib.sh`'s existing `_LOG_PR_PALETTE`/`pr_color_index`/`_sgr` (the same mechanism `pr_prefix` already used for the daemon's own `repo#pr` step lines) rather than inventing a second palette. `stream_format.py` itself stays colour-blind: `review-pr.sh`/`reply-pr.sh` compute `PR_COLOR_START`/`PR_COLOR_RESET` once per PR (hashing the same `"repo#pr"` key `log_set_pr_context` uses) and wrap the label text before passing it through `--label`, so `_log_color_enabled`'s TTY/`NO_COLOR`/`PR_LOG_COLOR` logic stays single-sourced in bash. A PR's colour is now identical whether the line came from the daemon's own step messages or from inside a `claude -p` call.

14. **Each review logs a total cost, not just one line per lens.** `total_cost_usd` from each call's terminal `result` event was only ever visible in that call's own one-line summary; seeing what a review cost meant hand-summing the log by eye. `stream_format.py` gained `--cost-out PATH`, writing the cost there on a real result event only (omitted on a timeout, matching `--raw-out`'s own empty-on-timeout contract). `review-pr.sh` sums every `*.cost` sidecar in the scratch dir with `find` (not a bare glob: every raw file, hence every `.cost` sidecar, is a dotfile, which `*` silently excludes without `dotglob`) and logs `total review cost: $X.XXX` once the review is done.

15. **`acquire_claude_slot` logs which slot it claimed and how long it waited.** The same dogfood round showed lens completion times ranging 35-519s with no way to tell whether a slow one was genuinely complex work or blocked on shared-pool contention: the completion time reported by `stream_format.py` is `claude`'s own measured duration, which starts only after a slot is already held, so it cannot distinguish "slow to run" from "slow to start." `acquire_claude_slot` takes an optional `label` argument; when given, it logs `<label>: acquired slot N/POOL_SIZE` and, if the wait was non-zero, `(waited Ns)`. Every call site now passes one (`"$lens_label lens"`, `"editor"`); the log call is safe inside `slot="$(acquire_claude_slot ...)"` because `log_info` always writes to stderr, never stdout.

16. **The status comment names the PR's base branch, unconditionally.** Considered, then rejected, following CodeRabbit's convention of skipping review entirely for a non-default base branch: this pipeline's per-PR state (reviewed-SHA trail, findings index) keys off the PR's own number and HEAD SHA, not its base, so it has no structural dependency on the base being the repo's default branch, and a stacked PR chain (this PR's base is another still-open PR's branch) is a real, intentional shape for incremental solo review, not an edge case to guard against. The one gap worth closing was operator confusion: nothing surfaced which branch a review's diff was actually scoped against. `gh pr view` now also fetches `baseRefName`; `review-pr.sh` appends `` (base: `X`)`` to `STATUS_SCOPE` whenever it's non-empty, always, not just when it differs from the default branch: that comparison would need its own `gh repo view` call for no real benefit, since the operator can already tell an unfamiliar branch name apart from `main` at a glance.

17. **Every `review-agent-*.md` definition gains an explicit `tools:` allowlist** (`Read, Bash, Grep, Glob, WebFetch`), where none existed before (meaning full tool access, confirmed via the agent listing's own "Tools: All tools"). A dogfood retry (sounds-abroad#192, same HEAD SHA re-run after a style-violation failure) showed the correctness lens invoking `SendMessage` and `ToolSearch`, orchestration tools meant for a top-level session, and narrating that it had "resumed the agent to get its raw JSON output," i.e. delegating part of its own single-purpose investigation to a sub-agent it had no reason to spawn. Separately, several lenses across multiple PRs called `ReportFindings`, a tool scoped to the unrelated `/code-review` skill's own output contract and explicitly documented as "use this only when the active code-review instructions tell you to," despite no lens prompt ever mentioning it: the name alone reads as generically applicable to "reporting findings," and no lens prompt says not to use it. Neither detour breaks the pipeline (the required ` ```json ` fence still gets emitted either way, and `merge_findings.py` reads only that), but both are wasted turns and cost, and the failure mode is unpredictable by construction: nothing in a lens's own prompt can reliably prevent a tool it can see from being reached for. Restricting to a real allowlist removes the capability outright rather than relying on prompt wording. `Write` and `Edit` are excluded too, on the same logic: one lens did legitimately write a scratch verification file, but did so through a `Bash` heredoc to an explicit throwaway path (observed in the same dogfood run, cleaned up with `rm -f` after), which the allowlist still permits; the dedicated `Write`/`Edit` tools additionally reach arbitrary existing paths, including ones inside the scratch clone a lens has no business modifying. Verified this restriction is honored for `claude -p` CLI (headless) invocations, not just Claude Code's interactive Task-based subagents, since that is how every one of these agents actually runs (ADR 0007).

18. **The per-review cost total logs on failure too, not just success.** The same sounds-abroad#192 run's first attempt ran all 5 lenses and the editor to completion, then failed on `apply_edits.py`'s style-violation check; that cost was real but never appeared anywhere in the log, since Decision 14's cost line only ran on the success path, right before `log_step "done"`. The summing logic moved into a `log_total_review_cost` function, called from both the success path and from `flip_status_failed` (the `EXIT` trap's failure handler), guarded only by the trap's own `rc -ne 0` check rather than its later status-comment-specific guards, so it fires on any non-zero exit regardless of how far the run got. It runs before `cleanup()` removes the scratch dir (the trap's own ordering, `flip_status_failed` then `cleanup`, guarantees the `*.cost` sidecars still exist when it reads them).

19. **Every `review-agent-*.md` and `review-agent-fix-check.md`/`review-agent-reply.md`/`review-agent-editor.md` gains an explicit final-message rule.** Confirmed live at least three times across a single dogfood day: a lens or `review-agent-fix-check` produces its correct fenced output in one turn, then a later turn (often triggered by flagging the lazyweb MCP prompt injection, ADR 0023's own security note) ends with only "already emitted above" or "nothing further to relay", no fence. `stream_format.py` reconstructs the terminal `result` event's text verbatim (its own documented, correct contract, matching plain-text-mode `claude -p`'s own behavior), so this is not a reconstruction bug: the model's actual final message genuinely carries no fence, and the correctly-produced earlier output is unrecoverable downstream. Confirmed concretely on sounds-abroad#193: `review-agent-fix-check` reached a real verdict, but the daemon logged `left open ... no json fence in fix-check output` and the thread stayed open under fix-check's own safe-bias, not because the code wasn't actually fixed. Each agent definition's Hard Constraints now states explicitly: re-emit the complete fence in the final message every time, even if it was already produced earlier, since only the final message is read.

## Boundary

This ADR ships exactly five lenses (default plus four domain lenses). It does not add a dedicated adversarial verify pass, and does not make the lens set configurable via `.env`, the five lenses are fixed in `review-pr.sh` for this cut. It does not change the confidence rubric, the severity/type taxonomy (ADR 0002), the format layer (ADR 0010), or the editor's subtract-only contract (ADR 0016): the editor still sees one merged draft and cannot add findings.

## Consequences

- Per-tick cost roughly quintuples for the review-agent leg: five `claude -p` calls instead of one. With the slot pool sized to the lens count, this lands mostly as concurrent API load rather than wall-clock; a solo PR's own lens phase takes roughly as long as its single slowest lens, not their sum.
- `MAX_PARALLEL` and `CLAUDE_SLOT_POOL_SIZE` now bound genuinely different resources (review-pr.sh process count vs. concurrent `claude -p` calls) and can be tuned independently. This is a real improvement over the initial cut's single dial, but it also means the *operator* is now responsible for picking a slot pool size that respects their actual Claude subscription/API concurrency headroom and local machine resources; this ADR does not and cannot compute a universally safe number.
- A location any lens is confident about clears the gate off the strongest score; a location every lens sees as marginal (all below threshold) is still dropped. Precision is not weakened, only recall is widened where independent reads agree or one lens is confident.
- `merge_findings.py`'s same-defect clustering is a body-text similarity heuristic (threshold 0.5), not semantic understanding. Two lenses' honest paraphrases of one defect can, at the margin, read dissimilar enough to stay split (a false negative: recall is not hurt, but the confidence-raising overlap benefit is missed for that pair), and in principle two narrowly-different defects with heavily overlapping wording could cluster wrongly (a false positive). Real-world lens bodies from divergent-enough prompts (this codebase's five lenses target different concern classes) are expected to sit clearly on one side of the threshold in practice; dogfooding will show whether it needs tuning.
- The dedup key is still exact `(path, line)`: two lenses flagging the same defect one line apart (e.g. the assignment vs. the read) merge as two distinct findings rather than one. This narrower gap remains, unaddressed here.
- A merged set exceeding `MAX_FINDINGS` truncates by severity then confidence rather than failing; a genuinely noisy multi-lens run (many independently-legitimate low-severity findings) can now drop lower-ranked real findings past the cap. Decision 8 surfaces the count in the posted summary so this is not silent, though the specific findings dropped are still not individually named.
- Concurrent lens output now shares one terminal; `stream_format.py`'s `--label` keeps lines attributable, but a foreground operator watching the daemon sees interleaved progress across up to `CLAUDE_SLOT_POOL_SIZE` lenses at once rather than one at a time, a real (if minor) readability cost against the old serial view.
- Under heavy contention (many PRs concurrently competing for the shared slot pool), individual PR latency becomes less predictable than the old serial-per-PR design; a PR can occasionally hit `PER_PR_TIMEOUT` and retry next cycle purely from contention, not a genuine hang. This is treated as acceptable given poll.sh's existing cheap-retry failure handling (state untouched on a failed dispatch), not as a gap to close.
- Adding a sixth lens later is a `bundle_operator_agents` glob hit (free, both the agent and its command) plus one entry in each of `review-pr.sh`'s three parallel arrays plus nothing in `merge_findings.py` or `status_failure_reason`, both already lens-count-agnostic, plus nothing in the slot pool mechanism itself (it is already lens-count-agnostic, just a shared counter). `CLAUDE_SLOT_POOL_SIZE`'s default and `PER_PR_TIMEOUT`'s default would both be worth a fresh look if a sixth lens meaningfully changes the realistic per-PR wave count they were sized against.
